# Celestia: working notes

Next.js (pages router, SSR) front end for the MLP Vector Club, on top of **Luna** (Laravel back end). It replaced **Winterchilla** (the PHP/Twig site, now read-only at old.mlpvector.club); Winterchilla's Twig templates and `assets/scss` are the reference for how a page is meant to look.

## Ground rules

- API types: the npm package `@went.tf/mlp-vectorclub-api-types`, which Luna builds from its committed OpenAPI document and publishes whenever that changes (`Publish API types` workflow). After changing the API: push Luna, wait for the publish, then raise the dependency in `apps/celestia/package.json` (`pnpm up @went.tf/mlp-vectorclub-api-types --latest`) and commit it with the change that needs the new API.
  Luna owns auth (`/sanctum/csrf-cookie`, `/users/signin`, OAuth, tokens): those types are hand-written in `src/types/auth.ts`; names that changed from the old contract are mapped in `src/types/api-alias.ts`.
- Build the UI from data: Winterchilla's rendered-HTML fields (`li`, `html`, `cgs`, `section`, `render`, `newhtml`, …) do not exist in Luna's API.
- Reads: `getServerSideProps` → fetcher (`src/fetchers/content.ts`, `ResourceService` forwards the visitor's cookie/authorization) → React Query hydration via hooks
  (`src/hooks/content.ts`). Writes: `useApiMutation` (`src/hooks/mutation.ts`) + a service in `src/services`; errors become `UnifiedErrorResponse`, show them with `describeApiError` /
  `fieldErrors`; invalidate the affected query keys instead of patching from responses.
- Send **JSON bodies, flags as 1/0** (a legacy of Winterchilla, which read JSON `false` as truthy). Always send an appearance's current `guide` on `PUT /appearances/{id}`.
- `GET /config` is fetched once and cached (`configFetcher`, `useConfig`); regex patterns are `{source, flags}` → `compilePatterns`.
- Utility pages (blending, picker, …): small modules, not one giant component per page: pure logic in `src/utils` (unit tested), one component per tool part, CSS modules for styles.
- Do not deploy or touch production; the user decides that. Commit identity and trailers follow the session instructions.

Edit and the validation errors were checked against Luna; the image and unbreak success paths were not (they need reachable images).

- **SSR auth:** the custom `wrapper.getServerSideProps` (`src/store/index.ts`) looks the visitor up with `requestUserFetcher` (only when the request has a cookie or Authorization header), stores it in `auth.initialUser` and `useAuth` uses it as the user query's `initialData`, so server and browser render the right visitor from the first paint. Verified with curl against the dev server and Luna (staff navigation appears for an admin token, not for a guest); not tried with a real Sanctum cookie session.

- **Password change** (account page, every signed in user for their own account): `PasswordForm` posts `{currentPassword?, newPassword}` to `POST /users/me/password`; Luna deletes all tokens on success so the sign-in dialog opens. Field errors checked against Luna; the success path was not (the seeded admin has an unknown password).

- **E-mail change** (account page, own address for everybody, developers may also ask for other users'): `EmailChangeForm` posts `{newEmail, currentPassword?}` or `{resend}` to `POST /users/{id}/email-changes`; `/users/verify?hash=&action=verify|block` (the link in Luna's mail) asks for confirmation and posts to `POST /users/email/verify`. Field errors checked against Luna. Luna's contract server (`scripts/serve-contract.sh`) logs outgoing mail (`MAIL_MAILER=log`): the link is in Luna's `storage/logs/laravel-cli-server-<date>.log` (look for `Subject: Verify your e-mail address`). The request (as admin for user 9001, no password needed, real-domain address, one try per address per 10 minutes) and the verify page's success were checked that way; the account page only lets users change their own address, which needs their password, so the form's own success state was not driven.

- **Accurate statuses for failed data fetches:** `handleDataFetchingError` (`src/utils/common.ts`) works out the HTTP status of a failed server-side fetch (`src/utils/fetch-failure.ts`; mapped errors keep it as `httpStatus`; no answer from the API is 503, any other failure 500) and records a failure for 429 and 5xx. The shared `wrapper.getServerSideProps` (`src/store/index.ts`) turns a recorded failure into a response with that status (and `Retry-After` for 429) and a `fetchFailure` prop, even when the page returned `notFound` (a missing page stays 404). `_app` then shows `FetchFailureView` instead of the page: for 429 the same kind of message as the sign-in form ("try again in N seconds") and a Try again button that stays locked until the wait is over (`useRateLimitLock`), for 503/500 a generic message; Try again re-runs the page's data fetching. Covered by `e2e/fetch-failures.spec.ts` and unit tests.

- **Visitor address on server-side requests** (`visitorAddress` in `src/services/service-class.ts`): requests made while rendering a page forward the visitor's address (`X-Real-IP`, else the first `X-Forwarded-For`, both set by nginx in front of Next.js) as `X-Forwarded-For`, next to the cookie and authorization, and always with `Referer: <the front end's address>` (the API's Sanctum accepts a session cookie only from requests that come from the front end, so the visitor's own referrer, e.g. a search engine, must not be forwarded), so the API throttles per visitor instead of counting everything as the Next.js server. On production the server-side `NEXT_PUBLIC_BACKEND_HOST` is `http://api.mlpvector.club`, which `/etc/hosts` points at the local nginx (so those requests already go through localhost, not Cloudflare).
- **Nutshell names** (the 2020 event mode, preference `cg_nutshell` on the account page): every appearance carries `nutshellNames` and `ownerId`. With the mode on, `NutshellLabel` (`src/components/colorguide/NutshellLabel.tsx`, rules in `src/utils/nutshell.ts`) shows one random name of an official appearance instead of its label, or the lowercased label when it has none; personal guide appearances are never renamed. Used in the guide list items, `AppearanceLink` (related appearances, linked shows), the full list cards, search suggestions and the appearance page heading; links and page titles keep the real label. The full list adds the real label, lowercased, to the "AKA" note of the renamed ones. `useNutshellMode` (`src/hooks/nutshell.ts`) holds the roll: names are random, so server renders and the first browser render show the real labels and the names appear right after hydration (once per component, so one name stays while it is on screen). With the mode on `Layout` also adds the `nutshell-names` class to `body` and loads Comic Neue as the old site did. Covered by `e2e/nutshell-names.spec.ts` and `src/utils/__tests__/nutshell.test.ts`.
- **Fixed by the browser checks:** the picker's About button was invisible, its area list overflowed the page, empty color fields were drawn as errors, and the blending reverser's row IDs came from a module-level counter that made server and browser HTML differ (keep IDs per component instance, never in module state).

## Verifying locally

- `turbo.json` has `cache: false` for `build`: the build also depends on the deployed git info (`BUILD_GIT_INFO`) and a cached run kept serving a stale `.next`.
- **Listen address:** `pm2.json` runs `start.js`, which loads `.env` and starts `next start` with `-H $HOST` (loopback if unset) and the port from `PORT`. Plain `next start` reads `PORT` but never `HOST`, so `HOST` in `.env` used to do nothing and production listened on every interface. Keep both in `.env`, not in pm2 options.

- **End to end tests** (`pnpm test:e2e`, run in CI by the `e2e` job of `.github/workflows/main.yml`, Playwright Test, `e2e/*.spec.ts`): Chromium against the real Next.js app (production build, real SSR and client routing, `webServer` in `playwright.config.ts`) with a stub API (`e2e/stub-api.mts`, a plain Node server: `GET /show` from a made-up list of any size, response delays set per page through `POST /__control`, fixed answers for the rest). `E2E_REUSE=1` reuses servers that are already running. The show page pagination is covered with many episode/other-entry count combinations plus the reported cases (page 3 → 2, 1 ↔ 2 over and over, back/forward, slow answers, bad page numbers). They are not part of `pnpm test` (the build is slow). They found that `useShowList` handed the server-rendered `initialData` to every page's query (fresh for 60 s, so other pages showed page 1's rows) and had overridden the global `keepPreviousData`.
- Unit/lint/types/build: `pnpm test`, `pnpm exec eslint .`, `pnpm exec tsc --noEmit`, `pnpm build` (run in this directory).
- **Browser tests that need a signed in visitor** (`/test-login/{id}`, `src/pages/test-login/[id].tsx`): with `E2E_TEST_LOGIN=1` on the Celestia server it asks Luna's test-only `GET /test/session-login/{id}` for a cookie session, passes the cookies on and redirects to `/` (or `?to=/path`); without the flag it is a 404. Luna only accepts a session cookie from requests that come from its configured front end (`FRONTEND_URL`, `localhost:3000` for the contract server), so serve Celestia at **http://localhost:3000**: `NEXT_PUBLIC_BACKEND_HOST=http://127.0.0.1:8766 NEXT_PUBLIC_FRONTEND_HOST=http://localhost:3000 NEXT_PUBLIC_CDN_DOMAIN=127.0.0.1 NEXT_PUBLIC_API_PREFIX=/api pnpm build`, then `E2E_TEST_LOGIN=1 pnpm exec next start -H 127.0.0.1 -p 3000`. The honeypots (`src/honeypot.ts`) look for Luna's session cookie by name: production's is `mlp_vector_club_session` (the default there), the contract server's is `luna_session`, so start that Celestia with `SESSION_COOKIE=luna_session` as well. Both applications read the same `SESSION_COOKIE` variable (Luna's own `session.cookie` setting), keep them equal.
- **Luna API:** Luna's `scripts/serve-contract.sh` (default `http://127.0.0.1:8766`, no `/api/v0` prefix); bearer token from `POST /test/login/{id}`.
- Run Celestia against either without touching `.env`:
  `NEXT_PUBLIC_BACKEND_HOST=<api base> NEXT_PUBLIC_FRONTEND_HOST=http://127.0.0.1:3100 NEXT_PUBLIC_CDN_DOMAIN=127.0.0.1 NEXT_PUBLIC_API_PREFIX=/api pnpm exec next dev -p 3100 -H 127.0.0.1`
  (only one dev server per checkout). OpenSearch-backed pages (guide search, autocomplete) answer 503 without ES.

## Two-step verification and passkeys

Luna answers `POST /users/signin` with **202** `{twoFactor: {challenge, methods}}` for an account with an authenticator app (nobody is signed in then). `signInThunk` resolves with that instead of a user, `authSlice` stores it in `auth.twoFactor` and moves the dialog to `AuthModalSide.TWO_FACTOR` (`TwoFactorForm`: code, recovery code, or a passkey; `backToSignIn` when the challenge ran out, a 401 with `expired: true`, mapped to `AUTHENTICATION_ERROR.expired`). Passkeys: `src/utils/passkeys.ts` wraps `@simplewebauthn/browser` (only one WebAuthn ceremony can run at a time: a click on a passkey button takes over from the autofill request, `manualCeremonyOpen` keeps the autofill loop from starting again meanwhile). `usePasskeyAutofill` (in `SignInForm`, active while the dialog is open) asks Luna for options and waits behind the e-mail field (`autoComplete="username webauthn"`), so the browser or password manager offers the saved passkeys in its dropdown and picking one signs in (the request's own `signInPasskeyThunk` state is `auth.passkey`, apart from the password form's). Never read `passkeysSupported()` while rendering (the server renders without knowing, hydration breaks): use `usePasskeysSupported()`. Account page, `#security` for everybody's own account: `TwoFactorSection` (password or, for accounts without one, a code of the app; QR code via `qrcode`, recovery codes shown once) and `PasskeysSection` (add, rename, remove); both read `GET /users/me/two-factor`, which also says whether the account has a password (`IdentityProofField`). Checked in headless Chromium with a CDP virtual authenticator against Luna's contract server (the authenticator answers the autofill request by itself, so a script has to switch the autofill off with an init script before testing the button). Tests: `authSlice.test.ts`, `TwoFactorForm`, `TwoFactorSection`, `PasskeysSection` browser tests.

## Sign up is DeviantArt only

No registration form: the dialog's sign-up side (`SignUpPanel`) explains that accounts are made from DeviantArt accounts, asks for the privacy policy to be accepted and opens the same DeviantArt popup as signing in (`useSocialSignIn`, shared with `SignInForm`). ## Forgotten passwords

"Forgot password?" in the sign-in dialog opens `AuthModalSide.PASSWORD_RESET` (`ForgotPasswordForm`: the address goes to `POST /users/password/forgot`, which answers the same for any address, so the form never says whether the account exists). The mail's link leads to `/users/reset-password?token=` (64 hex digits, listed as Disallow in robots.txt), which posts `{token, newPassword}` to `POST /users/password/reset`; Luna then ends every session of the account and leaves two-step verification on. A page's browser test cannot live under `src/pages` (every file there is a route): it is in `src/page-tests`. Checked in Chromium against Luna's contract server (its mail log holds the link).

## Linking a Discord account (account page)

The "Link account" button (`DiscordSection`) opens the sign-in redirect of Luna (`GET /users/oauth/signin/discord`) in a popup after leaving a note in localStorage (`noteDiscordLinkIntent`, `utils/oauth-popup.ts`, ten minutes, one use). The provider only knows one redirect address, so the callback page `/oauth/discord` can't tell linking from signing in by its address: for a signed in visitor `useDiscordLink` takes the note and, when it is for them, posts the code to Luna's `POST /users/{id}/discord` instead of signing in (success is reported to the opener like a sign-in, which refreshes the profile). Unit-tested (the note) and checked against Luna with a bad code; a real Discord round trip needs Discord's credentials and was not made. Luna commit that adds the endpoint: pin it with the `lock` command once pushed.

## Files served at /dist

`public/dist` holds `mlpvc-colorguide-schema.json` and `Import Swatches from JSON.jsx` (tracked despite the root `**/dist` ignore, linked from the guide index and the swatch dialog, CORS `*` from `next.config.js` `headers()`). `/dist/mlpvc-colorguide.json` is a rewrite to Luna's `GET /color-guide/export`, which builds the file live and is tested against the schema in Luna (`AdminTest::testExportFollowsTheSchemaOtherToolsRead`, schema copy in `tests/fixtures`). Keep the two schema copies equal. nginx on the production host that serves Celestia needs no `/dist` block of its own.
